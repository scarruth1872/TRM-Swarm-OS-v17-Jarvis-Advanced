VOLTAGE DOCTRINE - AS IMPLEMENTED AND AS MEASURED
  Doctrine (trm_uefi_kernel/host_council_server/src/voltage.rs):
    phi_v = (V_core/1.25)^2 * (f_actual/4000) * (V_ddr/1.35) * max(0.5, 1 - mem%/200)
    V_CORE_NOMINAL = 1.25 and V_DDR_NOMINAL = 1.35 are the DIVISORS (max boost /
    XMP). Rails in the numerator are 1.10 V core and 1.20 V DDR4 JEDEC.
    POLICY: "deny-by-default: a gate whose substrate is unmeasured does not open"
    The 0.9115 constant is FORBIDDEN - it was a hardcoded value while docstrings
    claimed hardware telemetry. evidence/PHI_V_ERRATA.txt supersedes it with
    0.4394 (min 0.4392, max 0.4395 over 8 samples at mem 72.3%, f 4000).

  Live readings now:
    GET /system/voltage ->
      phi_v 0.6884, measured false, status FALLBACK_UNMEASURED,
      source "FALLBACK: one or more telemetry reads failed; values are nominal,
      NOT measured", rails v_core 1.1 / v_ddr 1.2, gate open FALSE.
    GET /health -> voltage_measured false, voltage_phi_v 0.6884.
    GET /system/resources -> voltage_measured false, phi_v 0.6884,
      memory_percent 28.6, l3_sram_kb 32768.

  Three defects in that surface, measured:
    1. phi_v is inconsistent with its own memory reading. Solving the formula:
         mem 0.0%  -> 0.6884   (this is what is emitted)
         mem 28.6% -> 0.5899   (this is what /system/resources reports)
         mem 72.3% -> 0.4395   (this is the errata's measured value)
       The endpoint emits the mem=0 result while simultaneously reporting
       memory_percent 28.6 and memory_percent 0.0 in /health. A failed memory
       read is silently defaulting to 0.0, which makes phi_v optimistic by 17%.
    2. l3_sram_kb = 32768 (32 MB) while the actual 3900X L3 is 65,536 KB (64 MB),
       confirmed via Get-CimInstance Win32_Processor. The reported cache is half
       the real one.
    3. optical_phonon_thz 15.53 is emitted in the same object with no source,
       instrument or formula attached. Unfalsifiable as served.

  Doctrine is being obeyed in the one place that matters: measured=false is
  flagged, the gate stays closed, and the reason string refuses to substitute a
  nominal constant. That is correct. The arithmetic behind the number it does
  print is where the inconsistency sits.

CONSEQUENCE FOR "WE DON'T NEED AN LLM"
  The intended substitute is distilled ternary models + the K3 knowledge fabric.
  Measured today:
    - the native ternary doctrine model does not load (type 36 removed);
    - 3 of 4 Bonsai GGUFs are corrupt; 1 loads and is unwired;
    - 12GB of distilled _trits.bin has no reader;
    - the knowledge fabric's Python search is substring, not semantic;
    - the Rust fabric stats are literals, and the heavy fabric endpoints refuse
      to open because the voltage substrate is unmeasured.
  Chat therefore runs on an LLM because it is the only path that works. Removing
  the LLM requires, in order: (1) a ternary loader/engine, (2) a trained ternary
  model that loads, (3) semantic retrieval over the fabric, (4) a voltage sensor
  or an accepted measured-by-proxy policy so the gate can open.
